# platform/file-storage Specification

## Purpose
Defines where attachment contents are stored (the local filesystem or an S3-compatible bucket), the environment variables that configure it, the upload size limit, and the startup check that the storage is usable.

## Requirements
### Requirement: Storage backend is selected by environment variables
The backend SHALL store attachment contents in exactly one backend selected by
the `FILE_STORAGE` environment variable: `local` (the backend's filesystem) or
`s3` (an S3-compatible bucket). An unset or empty `FILE_STORAGE` SHALL select
`local`. Any other value SHALL stop the backend at startup with an error naming
`FILE_STORAGE` and its accepted values.

#### Scenario: Nothing is configured
- **WHEN** the backend starts with `FILE_STORAGE` unset
- **THEN** attachment contents are stored on the local filesystem

#### Scenario: Unknown backend name
- **WHEN** the backend starts with `FILE_STORAGE` set to `ftp`
- **THEN** startup fails with an error naming `FILE_STORAGE` and the values
  `local` and `s3`

### Requirement: Local storage uses a configurable directory
With `local` storage the backend SHALL store contents below the directory named
by `FILE_STORAGE_PATH`, defaulting to `./data/files` relative to the working
directory when unset. The backend SHALL create the directory if it is missing,
with permissions allowing access only to the backend's own user, and SHALL write
each file readable and writable only by that user. A resolved file path SHALL
never lie outside that directory.

#### Scenario: Directory does not exist yet
- **WHEN** the backend starts with `local` storage and `FILE_STORAGE_PATH`
  naming a missing directory whose parent is writable
- **THEN** the directory is created and startup continues

#### Scenario: Default path
- **WHEN** the backend starts with `local` storage and `FILE_STORAGE_PATH` unset
- **THEN** contents are stored below `./data/files`

### Requirement: S3 storage is configured by S3 variables
With `s3` storage the backend SHALL read `S3_ENDPOINT`, `S3_BUCKET`,
`S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` (all required), and `S3_REGION`,
`S3_USE_PATH_STYLE` (`true` or `false`, default `false`) and `S3_PREFIX`
(optional key prefix) as optional values. `S3_ENDPOINT` SHALL be an absolute
HTTP(S) URL. The backend SHALL work with any S3-compatible service and SHALL NOT
make stored objects publicly readable or hand out presigned URLs. With `local`
storage the `S3_*` variables SHALL be ignored.

#### Scenario: Required S3 variable missing
- **WHEN** the backend starts with `FILE_STORAGE=s3` and `S3_BUCKET` unset
- **THEN** startup fails with an error naming `S3_BUCKET`

#### Scenario: Prefix is applied
- **WHEN** `S3_PREFIX` is `my-cars/` and a file is stored
- **THEN** its object key starts with `my-cars/`

### Requirement: Unusable storage fails startup
The backend SHALL check at startup that the selected storage is usable: for
`local` storage by writing and removing a probe file in the directory, for `s3`
storage by confirming that the bucket exists and is accessible with the
configured credentials. If the check fails the backend SHALL exit with an error
naming the storage variables involved, instead of failing on the first upload.

#### Scenario: Directory is not writable
- **WHEN** the backend starts with `local` storage and a `FILE_STORAGE_PATH`
  the backend's user cannot write to
- **THEN** startup fails with an error naming `FILE_STORAGE_PATH`

#### Scenario: Bucket is not reachable
- **WHEN** the backend starts with `s3` storage and a bucket that does not exist
  or rejects the credentials
- **THEN** startup fails with an error naming `S3_BUCKET`

### Requirement: Maximum upload size is configurable
The backend SHALL read the maximum size of a single attachment in bytes from
`MAX_UPLOAD_BYTES`, defaulting to 10485760 (10 MB) when unset. A value that is
not a positive integer SHALL stop the backend at startup with an error naming
`MAX_UPLOAD_BYTES`.

#### Scenario: Default limit
- **WHEN** the backend starts with `MAX_UPLOAD_BYTES` unset
- **THEN** the maximum attachment size is 10485760 bytes

#### Scenario: Invalid limit
- **WHEN** the backend starts with `MAX_UPLOAD_BYTES` set to `10MB` or `0`
- **THEN** startup fails with an error naming `MAX_UPLOAD_BYTES`

### Requirement: Storage keys are generated by the server
The backend SHALL derive every storage key from the owning account's identifier
and a newly generated UUID, and SHALL never build a key or file path from a
client-supplied filename or other request input. Keys SHALL be independent of
the storage backend, so that files can be moved between backends by copying
them under the same keys.

#### Scenario: Filename with path segments
- **WHEN** a file named `../../etc/passwd.pdf` is uploaded
- **THEN** it is stored under a server-generated key and nothing is written
  outside the storage location

### Requirement: Storage configuration is documented
`backend/.env.example` SHALL document `FILE_STORAGE`, `FILE_STORAGE_PATH`,
`S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`,
`S3_SECRET_ACCESS_KEY`, `S3_USE_PATH_STYLE`, `S3_PREFIX` and `MAX_UPLOAD_BYTES`.
The project README SHALL state that a complete backup consists of the database
and the file storage, and that moving between storage backends is a manual copy.

#### Scenario: Example environment lists the variables
- **WHEN** the configuration test compares the variables the backend reads with
  `backend/.env.example`
- **THEN** every storage variable is present in both
